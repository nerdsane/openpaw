# Proof: D0 — crash resilience + self-healing corridors

**Date:** 2026-06-13
**Branch:** codex/searched-corridor
**Build:** release (`./target/release/temperpaw-server`)

## What was wrong (run 1, 2026-06-12/13)

The debug server aborted twice under v2 session concurrency (SIGABRT, then
SIGSEGV). Every interruption orphaned in-flight sessions, leaving Paths stuck
in Solving/Repaired/Challenged and Claims in Bridging with no re-drive. Run 1
only progressed through ~4 rounds of hand-dispatched salvage
(RequestChallenge / Fail+SubmitForBridge / RouteSettled).

## The fix (ADR-007)

1. **Release build for runs.** Same world load that aborted the debug build
   ran clean on release. Documented in the runbook.
2. **state_timeout re-drive** on every corridor wait state, replacing the old
   `allow_indefinite_states`: Path.Solving→ResumeRepair (re-spawn repairer),
   Path.Repaired→RequestChallenge (re-spawn adversary), Path.Challenged→
   ResumeCosting (re-run costing), Claim.Bridging→ResumeBridge (re-run the
   claim decision). All system-only in Cedar; all reuse existing spawn
   modules (no duplicate entities). verify_specs 10/10 (ADR-0050 enforce).

## Live proof

On the crash-orphaned run-1 world (en-019ebd69…, 14/15 claims terminal, the
last stuck Bridging on a dead-adversary Repaired route):

- `Claim.ResumeBridge` re-ran the claim decision deterministically and
  correctly **waited** (an in-flight Repaired route remained) — no spurious
  settle, no spawned session.
- `Path.RequestChallenge` (the Repaired-state self-heal action) re-spawned the
  adversary; the route scored; `Claim.RouteSettled` fired; the claim settled
  on its cheapest acceptable route; the world cascaded to a canonical path —
  with no hand-built sessions or routes, only the re-drive actions the
  timeouts fire.

## Honest scope

The re-drive **actions** are proven end-to-end. Auto-firing without an
external poke depends on the ADR-0056 hydration re-arm, which needs one
dispatch to the entity — present in any healthy run (a sibling event pokes
the claim), but a fully cold-orphaned entity after a quiet restart needs a
proactive boot sweep, noted in ADR-007 as a follow-up. Given release-build
stability (the primary G4 fix), the common mid-run session-death case is
fully covered. For the scarred run-1 only, the timeout actions were dispatched
manually to stand in for the boot poke.
